Start with something that works:

```bash
docker run -d nginx
```

One command, one <Term>container</Term> running from one
<Term term="Container image">image</Term>. Nothing here needs a cluster, and for
a personal project nothing here ever will.

So this lesson does not argue that you need Kubernetes. It breaks the command
above, one problem at a time, and asks what you would have to build to survive
each one.

> **Interactive.** Five scenarios, each one breaking the previous fix. Not built
> yet.

First the container dies. You add a restart policy, which is easy, and Docker
already does it for you.

Then the machine dies, and the restart policy dies with it. Something outside
that machine has to notice and start the container somewhere else, which means
you need a somewhere else, plus something that knows about both machines.

Then you need ten copies. Ten <Term term="Replica">replicas</Term> spread over
three machines, and you have to know which machine still has room. You are
writing a scheduler now.

Then you need to update them. Not all at once, because that is an outage. A few
at a time, checking that the new ones work before you remove the old ones, and
stopping if they do not.

Then callers have to find them. The set of running containers changes every time
one is replaced, so nobody can hard-code an address. You need a stable name that
resolves to whichever containers happen to be alive.

Each fix is reasonable on its own. Together they are a distributed system, and
you did not set out to write one. That is the gap Kubernetes fills, and it is
also why Kubernetes is as large as it is.
