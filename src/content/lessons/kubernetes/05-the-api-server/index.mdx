Last lesson was about how you write objects. This one is about where they
actually get handled.

## There is one door

The <Term>API server</Term> is the ONLY component in the cluster that anything
talks to.

You submit an object to it. A controller reads objects from it. A machine asks it
what it should be running. Nothing goes around it, and nothing reads or writes
the database behind it directly, not even the components sitting on the same
machine.

That's a bigger deal than it sounds. Every read and every change goes through one
point, so anything the cluster wants to enforce, or notice, only has to be built
once.

## It's just an HTTP API

There's nothing exotic about the protocol. Objects are resources with URLs, and
the operations are the usual ones:

```text
GET    /api/v1/namespaces/shop/pods
GET    /api/v1/namespaces/shop/pods/web-7d4f
POST   /apis/apps/v1/namespaces/shop/deployments
PATCH  /apis/apps/v1/namespaces/shop/deployments/web
DELETE /apis/apps/v1/namespaces/shop/deployments/web
```

The path is just the object's identity spelled out: which API group, which
version, which namespace, which kind, which name. Cluster-wide kinds simply have
no namespace segment.

<Term>kubectl</Term> is an HTTP client for this and not much else. Prove it to
yourself once:

```bash
kubectl get pods -v=8
```

You get the request it sent, the headers, and the JSON that came back. A
`kubectl` subcommand is really just a convenience over one or two of these calls,
and anything you can do with it you can do with `curl` and a credential.

## Six gates

A request that changes something doesn't go straight into the store. It walks a
fixed sequence, and each step asks one question. The order is the interesting
part.

Two of those gates can change or refuse your object after you've already been
allowed to send it. That's why what comes back out of `kubectl get` isn't always
the file you put in, and why a request can pass one gate and get rejected three
gates later.

## What the response means

When the write succeeds you get the stored object back, with two things attached
that you didn't send: a name for anything you left to be generated, and a version
number.

```yaml
metadata:
  name: web
  namespace: shop
  resourceVersion: "41822"
  uid: 6b1c0b1e-3a7a-4b5c-9f0f-2a5f0f2b8e11
```

The <Term>resourceVersion</Term> marks *when* in the cluster's history this
object was last written. It's got nothing to do with your app's version.

Underneath it's one counter that every write in the cluster bumps, so the numbers
only go up and a bigger one always means later. The field is still documented as
opaque though, and both things are true for a reason: the ordering is what lets
the *server* answer "everything since 41822", and the opacity is what stops *you*
building on a detail the project wants to be free to change. You can compare two
of them for equality, and you can hand one back.

Handing one back is the useful part. Send an update carrying the version you
read, and the write only succeeds if nothing has touched the object since:

```text
PUT /apis/apps/v1/namespaces/shop/deployments/web    resourceVersion: "41822"

409 Conflict
Operation cannot be fulfilled on deployments.apps "web": the object has been
modified; please apply your changes to the latest version and try again
```

So two things editing one object can't silently overwrite each other. The loser
gets told to read the current object and try again. (This is again reinforcing
the concept of eventual consistency)

## A watch is not a queue

You could just re-read everything on a timer. It would work, and it would be
awful. So the API server offers one more verb:

```text
GET /api/v1/namespaces/shop/pods?watch=true&resourceVersion=41822
```

The connection stays open and the server sends a small entry every time a pod in
that namespace is added, modified or deleted, starting from the version you
named. That's a <Term>watch</Term>, and it's how everything in the cluster stays
current without polling.

It's very easy to read that as a message queue, and it really isn't one. There
are two differences and both matter:

| A queue | A watch |
|---|---|
| Delivers every message, eventually | Can drop you, and does |
| You are expected to process each one | You are expected to re-read the object |
| Missing one loses information | Missing one loses nothing you cannot re-read |

A watch can just end. The connection breaks, the server restarts, or the history
you asked to resume from got discarded because it was too old. You don't recover
the lost entries, because they aren't recoverable. You list everything again and
carry on from the version that list came back with.

So nothing built on this can treat an entry as an instruction, because then
missing an entry would be a missing instruction.

## What it doesn't do

The API server doesn't start containers. It doesn't decide which machine anything
runs on. It doesn't notice that you asked for three and have two.

It answers requests and it writes objects down. Everything in the cluster that
looks like it's *doing* something is a separate program that got its information
the same way you would have, by asking this one.
