Lesson one ended with a list of five things you would have to build to run
containers seriously. Lesson two handed you the second item on it and made you
do the job by hand: a written specification, a look at what is actually there,
and a change to close the gap.

Make that loop run on its own, give it the other three items and somewhere to
run things, and you have Kubernetes. That is the actual shape of the
system, not a simplified version of it that gets corrected later.

A <Term>cluster</Term> is a set of machines managed as one pool of compute. You
stop addressing individual servers and start addressing the pool. It splits in
two:

```text
              Kubernetes
                   │
       ┌───────────┴───────────┐
       │                       │
 Control plane             Worker nodes
 (decides)                 (run things)
```

The <Term>control plane</Term> holds the desired state and runs the loops that
drive reality toward it. It makes decisions, and it does not run your workloads.

A <Term>node</Term> is a machine that does run them. It takes instructions about
what should be running locally, makes that true, and reports back what is
actually happening.

That split explains a fair amount of Kubernetes behaviour before you meet it. If
the control plane goes down, your running workloads keep running, because
nothing is deciding anything new but the nodes carry on regardless. If a node
goes down, the desired state survives, because it was never stored there.

The rest of this phase is all control plane. Workloads come back in phase three.
